# X 平台限速规则检索汇总与三层滚动编排策略

本文对照 **X 官方 API v2 限速文档**、**Web 端社区实测上限** 与本仓库在 **`2026-11-14` 真实账号写入实测/封号复盘**（[`X-WRITE-ENDPOINTS-2026-11-14.md`](reports/X-WRITE-ENDPOINTS-2026-11-14.md)、[`POSTMORTEM-SUSPENSION-2026-11-14.md`](reports/POSTMORTEM-SUSPENSION-2026-11-14.md)），给出主动关注、发帖、回复、点赞与转发的安全编排配额。

---

## 一、X 各核心动作限速真相（API v2 vs Web 实测风控）

| 动作类型 | 关键端点 | 官方 / 社区上限口径 | 本项目实测踩线特征 | 运行时真实瓶颈 |
|---|---|---|---|---|
| **主动关注** (`follow_profile`) | `friendships/create` (Web)<br>`POST /2/users/:id/following` (API v2) | API v2：`50` 次 / `15 分钟`<br>普通号每日硬顶：`~400/天`（Premium `~1,000/天`）；社区安全建议 `15–20/小时` | **Web 每 `900s` 窗实测上限 `15` 次**（第 16 次返回 `HTTP 429`）；新号累计约 `215` 次触发 **`code 161`（HTTP 403 长期额度耗尽）** | **最严**：受短窗 `15/900s` 与账号累计关注比双重约束 |
| **主动发帖** (`publish_post`) | `CreateTweet` (Web)<br>`POST /2/tweets` (API v2) | API v2：`100` / `15 分钟`（单用户），`10,000` / `24h`（应用）；未认证 Web 端日常上限约 **`50` 原创/天** | 短时（~30 分钟）内高频连发会触发反垃圾降权或限流；连发内容重复会被静音/折叠 | 原创贵在质量与定时散布，切忌连珠炮发送 |
| **串门回复** (`reply_post`) | `CreateTweet` (`in_reply_to`) | 共享发帖与回复池（Web 约 `200` 回复/天上限） | 无上下文短句硬回或固定话术重复最易招致人工举报 / 机器人标记 | 受内容去重 + 频率双约束 |
| **主动点赞** (`like_post`) | `FavoriteTweet` (Web)<br>`POST /2/users/:id/likes` | 响应头常见 `x-rate-limit-limit: 500`；软上限约 `500–1,000/天`，社区建议 `<= 50–100/小时` | 即使响应头剩余 `471/500`，**Scarecrow `code 283`（HTTP 200 内嵌错误）**仍会提前全线拦截新号/突发点赞 | **不是配额问题，是行为风控防火墙** |
| **主动转发** (`repost_post`) | `CreateRetweet` (Web) | 单窗 `4/波` 仍返回 200 | **`2026-11-14` 封号复盘**：中位间隔 `7 秒` 连转（1,047 次 / 45.6h）在 429/283 之后继续强冲，直接升级 **`code 141` 封号** | 绝不以“接口还返回 200”作高频转发理由 |

## 二、X MCP 落实的三层滚动限速编排（`evaluate_rolling_windows` + `slice_wave_for_rate_limits`）

只看“今日 24 小时总上限”不够安全——连续两波隔 10 分钟跑完 15 次关注就会当场撞翻 X 的 `900 秒` 滚动窗。因此 [`src/account_orchestrator.py`](../src/account_orchestrator.py) 与 [`server.py`](../server.py) 增加了 **15 分钟（`900s`）+ 1 小时（`3600s`）+ 24 小时（本地日历日）三层硬闸门**：

| 动作 | 安全 15 分钟上限 (`900s`) | 安全 1 小时上限 (`3600s`) | 默认建议每日目标 (`prepare`) | 随机人类间隔 / 额外保护 |
|---|---:|---:|---:|---|
| **主动关注 (`follow_profile`)** | **`10`**（比 X `15/900s` 预留 5 个缓冲槽） | **`24`** | **`40/天`**（稳健防 `161`；成长期可显式调高但仍受 `10/15m` 与 `24/h` 节流） | `44–90s` 起跳；粉丝/关注比超 `2.5x`（`following>=50`）自动熔断停关 |
| **主动发帖 (`publish_post`)** | **`2`**（单波微批最多 **1** 条独立贴） | **`3`** | **`2–5/天`** | **连续两条独立原创帖强制间隔 `>= 1,800 秒（30 分钟）`**；串推（Thread）作为整条内容顺序发出 |
| **串门回复 (`reply_post`)** | **`6`** | **`18`** | **`25–45/天`** | `75–155s` 随机间隔；单波同一作者最多回 `1` 条；超短/未知意图静默跳过 |
| **主动点赞 (`like_post`)** | **`14`** | **`36`**（严格压在 `< 50/小时` 安全区） | **`60/天`**（成长高互动模式可显式设 `120–150/天`，受 `36/h` 匀速铺开） | `22–60s` 分布；访问主页时最多顺手点 `1–2` 赞 |
| **精品转发 (`repost_post`)** | **`1`** | **`2`** | **`<= 2–4/天`** | `150–360s` + 至少间隔 `8` 个其它动作，且必须通过 `score_technical_quality` 门槛 |

## 三、触发限流与拒绝信号时的停机契约

1. **前置滚动限流避让（不浪费 X 请求）**：`x_autopilot(action="run_wave")` 切片前先调 `slice_wave_for_rate_limits`；若 `15m` 或 `1h` 窗口已满，直接返回 `reason: "ROLLING_RATE_LIMIT_PACING"` 与准确的 `next_retry_epoch`，等到旧窗口滑出再继续，避免撞上 `HTTP 429`。
2. **硬拒绝信号立即熔断（`evaluate_circuit_breaker`）**：
   - `429 / X_RATE_LIMITED`：按 `reset_epoch` 冷却等待，绝不在窗口内重试同一波次。
   - `283` / `161` / `141` / `37` 或连续 `2` 次 `ACTION_UNCERTAIN`：全线进入长期冷却（`4–24h`），**严禁把其它动作类型当替代通道继续刷量**。
