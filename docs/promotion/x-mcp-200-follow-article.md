# 10 分钟关注 200 人？我们把这个噱头拆成可验证的 X MCP

> X MCP 不是一段“点按钮脚本”。它是一层让 Agent 规划、分块、确认、执行和复核 X 社交动作的 MCP 接口。

## 先说结论

“10 分钟关注 200 人”是一个很好的产品钩子，但截至 2026-10-27，它不是我们的已验收事实。

真实实验给出了两个不同答案：

- **点击速度够快**：关注周期小样本 p50 为 1.16 秒。按这个数字串行外推，200 次约 3.9 分钟。
- **真实成功率不够**：历史 18 次连续关注中，18 个按钮都显示 Following，但独立复核只有 8 次真正生效，有效率 44.4%。

所以，我们不会把“按钮变了”宣传成“200 人已成功关注”。真正值得展示的是：Agent 可以把大任务拆成可确认的块，每个动作都有租约和结果，失败不会被假装成成功。

## 这是什么产品

X MCP 给支持 MCP 的 Agent 一层可调用的 X 工作接口。

Agent 可以先读取公开资料，或者读取主人授权的浏览器页面。需要改变账号状态时，系统先生成计划，再等待确认。确认后，任务会拆成独立动作。每个动作都由 Agent 或内置浏览器执行器领取，并返回后置验证结果。

当前有两条执行路径：

| 路径 | 执行者 | 适合场景 |
| --- | --- | --- |
| 内置浏览器 | MCP 自带 Chromium 执行器 | 主机把浏览器交给 MCP 管理 |
| 外部 Agent | 其他 Agent / Computer Use | Agent 自己控制浏览器，再通过 MCP 回报证据 |

两条路径使用同一套确认、claim token、lease 和 postcondition 规则。

## 200 规模怎样进入接口

最新批次接口支持：

| 动作 | 单个计划上限 | 默认分块 |
| --- | ---: | ---: |
| 点赞 | 200 | 每块 20 个 |
| 转发 | 10 | 每块 20 个 |
| 评论 | 200 | 每块 20 个 |

三类动作合计最多 410 个。默认每 20 个动作组成一块，因此 410 个动作会形成 21 块。

一个外部 Agent 的执行循环很简单：

1. 调用 `x_browser_next_action(batch_id, chunk)` 领取一个动作。
2. 在自己的浏览器里执行这一个动作。
3. 调用 `x_browser_complete_action` 返回结构化结果和证据。
4. 重复直到当前块返回 `idle`。
5. 调用 `x_interaction_batch_status` 查看每一块的进度。

如果 Agent 中途退出，租约过期后动作变成 `uncertain`。系统不会偷偷把它重新执行。

## 我们真正测到了什么

### 本地 MCP 层

| 测试 | 结果 | 口径 |
| --- | ---: | --- |
| 512 客户端 HTTP mock | 994.06 RPS，0 错误 | 本地机器，无 X 网络，无模型调用 |
| 2048 客户端极限观察 | 533.08 RPS，0 错误 | 峰值内存约 658.68 MB |
| `tools/list` | p50 0.003 ms | 5000 次进程内 mock 调用 |
| 视觉兜底 | 27/27 | 真实 Chromium，合成页面 |
| 兼容矩阵 | 42/42 | 视口、DPR、语言、主题组合 |

这些数字说明：MCP 协议和本地排队不是主要瓶颈。真实任务的耗时主要来自浏览器启动、X 页面渲染、网络、外部限流和模型决策。

### 真实 X 只读

真实公开 profile 冷读耗时约 1.31–1.59 秒。快速读取时间线时，X 返回过 HTTP 429。

这说明真实 X 的吞吐不能用本地 RPS 代替。我们把 429 原样记录，而不是把它算成“空结果”。

### 真实浏览器写入小样本

以下数据来自本机 `@guoz7777` 专用浏览器 profile 的可逆测试。点赞和关注都在测试后撤销，评论都在测试后删除。

| 动作 | 样本 | p50 | 说明 |
| --- | ---: | ---: | --- |
| 关注周期 | 5 | 1.16 秒 | 导航、定位、点击、状态等待 |
| 点赞周期 | 4 | 1.65 秒 | 包含撤销前的验证等待 |
| 评论周期 | 3 | 2.22 秒 | 发布后定位并删除 |

这些是“点击周期”，不是“服务端成功率”。X 可能先更新前端按钮，再静默丢弃服务端写入。因此批量系统必须继续复核。

## 成本怎样算

浏览器路径本轮使用的 X API credits 为 0 美元。它不需要把 X API Key 放进 Agent 提示词，也不读取 Cookie、密码或浏览器存储。

但 0 美元 API credits 不等于 0 成本：

- Agent 模型会产生输入和输出 token 成本。
- 浏览器会占用 CPU、内存和运行时间。
- 失败后的复核、退避和截图会增加时间。
- 托管服务还要增加机器、带宽、日志和租户隔离成本。

作为 API 路径的参考，如果“每次用户交互创建 0.015 美元”的已知假设适用，200 次写入约为 3 美元。这个数字不属于本轮浏览器实测，也没有计读取、重试和限流。

## 对外怎么说

推荐标题：

> 10 分钟关注 200 人？我们用真实 X 数据拆解 Agent 自动社交的速度与成功率

推荐正文：

> 我们做了一个 X MCP，让 Agent 可以读取、规划、分块执行并复核社交动作。小样本里，关注点击周期 p50 约 1.16 秒；但历史 18 次连续关注的服务端有效率只有 44.4%。所以我们不把按钮变色当成功，而是把每个动作做成有确认、有租约、有后置验证的工作单元。当前接口支持 200 点赞、10 转发和 200 评论的分块计划，支持外部 Agent 领取动作并回报证据。真实 200 关注仍在工程验收中。

这段说法同时有钩子、数据和边界。它比“10 分钟保证关注 200 人”更可信，也更容易让开发者复现。
